# RouteMapper — Development Workflow

This document describes the branching strategy, deployment environments, and release process for the RouteMapper app. It exists so that any developer (or Claude) picking up this project has a clear picture of how changes move from idea to live.

---

## Repository

**GitHub:** https://github.com/rogsaunders/routemapper

---

## Environments

| Environment | Branch | URL |
|---|---|---|
| **Production** (live, Lachie's URL) | `main` | Netlify production URL |
| **Staging** (development testing) | `develop` | `https://develop--[site-name].netlify.app` |
| **PR Previews** | Any open PR | Auto-generated by Netlify per PR |

> Nothing goes live to Production unless deliberately merged to `main` via a Pull Request. Branch protection is enabled on `main` — direct pushes are blocked.

---

## Branch Structure

```
main          ← live / production (protected)
develop       ← integration branch for all active development
feature/xyz   ← individual features, branched from develop
hotfix/xyz    ← urgent fixes, branched from main
```

---

## Day-to-Day Workflows

### Regular Feature Development

1. Create a branch from `develop`: `feature/what-youre-building`
2. Do the work and commit
3. Open a Pull Request: `feature/...` → `develop`
4. Netlify auto-deploys a preview URL for the PR — test there
5. Merge the PR into `develop` — staging URL updates automatically
6. When ready to release, proceed to the Release Process below

### Urgent Hotfix (something broken in production)

1. Branch directly from `main`: `hotfix/description`
2. Apply the fix and commit
3. Open a PR: `hotfix/...` → `main`, merge — production updates immediately
4. **Important:** immediately open a second PR from `main` → `develop` to back-merge the fix, so it isn't overwritten at the next release

### Planned Release

1. Open a PR: `develop` → `main`
2. Give it a descriptive title: e.g. *"Release v0.5 — route rendering improvements, GPX export fix"*
3. Review the diff — this is the governance checkpoint. Only merge when satisfied.
4. Merge → production updates
5. Tag the release on `main`:
   - Go to GitHub → Tags → Create new tag: `v0.5.0`
   - Write a short description of what's included
   - This creates a permanent, dated record of what Lachie (or any user) received and when

---

## Versioning Convention

`v[major].[minor].[patch]`

- **patch** (`v0.4.1`) — hotfixes, no new features
- **minor** (`v0.5.0`) — planned releases with new features or improvements
- **major** (`v1.0.0`) — significant milestone (e.g. public launch)

## Quick Reference

| Situation | Branch from | PR target | Then |
|---|---|---|---|
| New feature | `develop` | `develop` | Release when ready |
| Bug found in staging | `develop` | `develop` | Release when ready |
| Bug found in production | `main` | `main` → then back-merge to `develop` | Tag patch version |
| Planned release | — | `develop` → `main` | Tag minor version |
