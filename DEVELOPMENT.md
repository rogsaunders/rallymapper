# RouteMapper — Development Workflow

This document describes the branching strategy, deployment environments, and release process for the RouteMapper app. It exists so that any developer (or Claude) picking up this project has a clear picture of how changes move from idea to live.

---

## Repository

**GitHub:** https://github.com/rogsaunders/routemapper

---

## Environments

| Environment | Branch | URL |
|---|---|---|
| **Production** (live, Lachie's URL) | `main` | Netlify production URL |
| **PR Previews** (staging) | Any open PR | Auto-generated by Netlify per PR |

> Nothing goes live to Production unless deliberately merged to `main` via a Pull Request. Branch protection is enabled on `main` — direct pushes are blocked.

There is deliberately no persistent `develop`/staging branch. A `develop` branch existed previously but drifted ~100 commits out of sync with `main` — every feature PR was merging straight to `main` while `develop` sat still, so it stopped meaning anything and was removed (2026-08-28). Netlify's per-PR deploy preview now serves as the staging step: every PR gets its own live URL to click through before it merges, without a second branch that can silently rot.

---

## Branch Structure

```
main          ← live / production (protected)
feature/xyz   ← individual features, branched from main
fix/xyz       ← bug fixes, branched from main
hotfix/xyz    ← urgent production fixes, branched from main
```

All branches come from `main` and merge back into `main`. There's no other branch to keep in sync.

---

## Day-to-Day Workflow

1. Create a branch from `main`: `feature/what-youre-building`, `fix/...`, or `hotfix/...` for something urgent — the prefix is just for readability, they all behave the same way.
2. Do the work and commit.
3. Open a Pull Request into `main`.
4. Netlify auto-deploys a preview URL for the PR — this is the staging step. Click through the actual change there before merging: inject test data if needed, check the console, confirm the specific thing the PR changes.
5. Merge → production updates immediately.

That's it — no release PR, no back-merge step, no second branch to remember.

## Versioning Convention

`v[major].[minor].[patch]`

- **patch** (`v0.4.1`) — fixes, no new features
- **minor** (`v0.5.0`) — notable features or improvements
- **major** (`v1.0.0`) — significant milestone (e.g. public launch)

Tagging is no longer tied to a release process — there's nothing to batch anymore, since every merge to `main` is already live. Tag on `main` (GitHub → Tags → Create new tag) when it's useful to have a dated record of what shipped — a notable feature, a milestone, or before a period of higher-risk changes — not as a required step on every PR.
